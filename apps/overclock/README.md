# DRIFT

Native SBF reverse-engineering/runtime challenge with an exact-byte LiteSVM replay checker.

The vulnerable artifact is a small native Solana program implementing a funded yield vault. Its
accrual path trusts the `Clock` sysvar, performs wrapping elapsed-time arithmetic, and credits the
result as withdrawable value. The organizer checker loads and executes the exact ELF placed in the
player kit; JavaScript is retained only as a modeling oracle and cannot emit a flag.

## Authoritative architecture

- `native/program/` — native non-Anchor Solana program and pinned SBF build lockfile;
- `player-kit/dist/overclock_vault.so` — genuine stripped SBF ELF generated by `npm run build:sbf`;
- `native/harness/` — LiteSVM target seeding, constrained transaction/Clock replay, invariant checker,
  and the only HMAC flag path;
- `src/runtime.mjs` — non-authoritative JavaScript oracle for fast accounting tests;
- `test/runtime.test.mjs` — model parity and adversarial tests.

Deposits are real System Program lamport transfers from a rent-exempt attacker account into a
program-owned vault. An independent organizer fee payer covers transaction fees, so the invariant is
exactly measurable:

```text
net withdrawals == attacker spendable-balance profit == drain of the original vault reserve
```

All three values must meet the per-team threshold. Gross deposit/withdraw volume cannot solve.

## Toolchain

- Solana/Agave `cargo build-sbf` 2.3.x (the local verified build used 2.3.13/platform-tools 1.48);
- Rust 1.86 or newer for LiteSVM 0.13.1 (`cargo +stable` is used by the scripts);
- Node.js/npm for the convenience scripts.

## Build and test

```bash
npm run build
npm test
```

`npm test` rebuilds the SBF artifact first, then runs both model tests and native integration tests.
The native suite verifies that the reported SHA-256 is the ELF actually loaded by LiteSVM.

## Organizer commands

```bash
npm run target -- team-local
npm run demo -- team-local

# Reads {"teamId":"...","steps":[...]} from stdin; never emits a flag.
npm run replay < submission.json

# The only scored path. FLAG_SECRET must be at least 32 bytes.
FLAG_SECRET='replace-with-a-real-32-byte-secret' npm run check < submission.json
```

The accepted replay boundary is deliberately narrow: canonical deposit/accrue/withdraw transactions
and signed 64-bit `Clock` values, at most 32 steps. Arbitrary account writes, program replacement, and
reported client balances are not representable in the submission schema.

## Artifact verification

```bash
file player-kit/dist/overclock_vault.so
strings player-kit/dist/overclock_vault.so \
  | grep -iE 'unix|timestamp|elapsed|interest|last_ts|reserve|vault|balance'
```

The first command must identify a stripped ELF for the Solana SBF architecture; the strings command
must produce no challenge-term matches.

## Remaining deployment boundary

This directory now contains a real program and exact execution checker. Event deployment still needs
the repository-wide instancer/service layer to isolate teams, rate-limit submissions, retain the
server-side flag secret, and publish only `player-kit/` rather than organizer source and reference
steps. Accordingly, target metadata reports `exactReplayReady: true` but keeps
`productionReady: false` until that service boundary is connected.
